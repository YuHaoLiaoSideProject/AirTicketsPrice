## 三、三種狀態統計（**明確區分，不混為一談**）

| 狀態 | 判定依據 | 次數 | 佔比 |
|---|---|---|---|
| `有票價` | HTTP 200 且 `histogram[].fares` 非空 | 3 | 38% |
| `API 回 200 但無資料` | HTTP 200、`histogram` 有該日期、但 `fares: []` | 5 | 62% |
| `請求失敗` | 4xx / 5xx / timeout / 非 JSON | **0** | 0% |

補充證據（查無時不是「整包空」，而是「日期在、fares 空」）：

```json
// 2026-11-07 完整回應的關鍵欄位
{
  "histogram": [{"date": "2026-11-07", "fares": []}],
  "buckets": {"avg": {"priceRange": {"minimum": 17057.445, "maximum": 17526.555},
                      "totalResults": 0}, ...},
  "responsePriceStats": { ... }
}
```

→ **`buckets.avg.totalResults = 0`**，且 `responsePriceStats` 存在但無有效樣本。這證實「查無票價」是**資料集缺漏**，不是錯誤碼、也不是 `null`。實作時必須把它記成「無資料」而不是 `price = 0` 或 `null`（避免污染下降偵測）。

## 五、token 行為

| 觀察 | 結果 |
|---|---|
| 首頁 GET 次數 | 1（整個探測輪次只抓一次首頁，key 快取在記憶體） |
| 每組請求是否需換 token | ❌ 不需要 |
| 同一把 `em-api-key` 連續使用 10 次 | 全部 HTTP 200（0 次 401/403） |
| token 失效事件 | 無 |
| 需不需要自動重取 | **同一輪不需要；跨輪需要（48h 效期）** |

腳本採取的防護（本次未觸發，但已實作）：

- `429` / `403` → **立即停止整個探測**，把 `aborted` 記進結果，不重試、不換 IP、不換 UA。
- `401` → 重取首頁一次（`is_refresh=True`）後重試該次查詢；再失敗則記為請求失敗。
- 每組之間 `sleep` 2–4 秒（隨機），實測 2.5–4.0 秒。
- `--max-requests`（預設 15）硬性上限，超過即停止逐組探測。

> `em-api-key` 是**站方公開發給任何訪客的 site key**，不是登入態。仍不應寫進 repo 或日誌（腳本只印遮罩後的 `HeQp…3pah`）。

## 七、關鍵方法學發現：區間查詢 1 次 = 逐組查詢 8 次

區間查詢（`departure.start=2026-11-07`、`end=2026-12-26`、`weekDays=["SAT"]`、`tripDuration=1..1`）一次回傳 50 天的 histogram，其中有價日期為 `11-28 / 12-05 / 12-19`，**與 8 次逐組查詢的結果集合完全相同**。

→ 兩個結論：

1. 逐組查詢的空值**不是**查詢形狀造成的假性空值（這條必須驗，否則 38% 這個數字就不能信）。
2. 若真的要接進排程，**用 1 次區間查詢取代 N 次逐組查詢**，成本降到 1/8，也大幅降低被 Akamai 盯上的風險。逐組查詢只值得用於「已知有價日期抓細節」。

## 八、建議

### 8.1 該不該接進排程？

**不建議作為主要票價來源。** 理由：

1. **覆蓋率 38%** —— 62% 的週末拿不到任何價格，等於每 8 週只有 3 週有觀測點，「票價下降偵測」在這條航線上會大量漏報，而漏報在使用者眼中與「沒降價」無法區分。
2. **沒有班號／時刻** —— `histogram` schema 無 `flightNumber`，與既有 `data/` schema（`outbound_flight_no`、起降時刻）不相容；接進去只能當「航線最低價」的旁證，不能當 flight-level 資料。
3. **空值語意不明** —— 售完／未開賣／資料集缺漏三者無法區分（本次 11/07 距今僅 7 天仍查無，偏向「資料集缺漏」）。

若仍要接，定位應是**「華航歷史最低價參考」而非逐航班報價**，且必須標記 `data_completeness: "Partial"` 之類的語意。

### 8.2 若真的要做，需要的防護

| 防護 | 做法 |
|---|---|
| 請求量 | 用**一次區間查詢**（1 請求/航線/週）取代逐組；全站每週 ≤ 2–3 請求 |
| 頻率 | 每週 1 次（跟現有 `weekly-crawl-*.yml` 同節奏），不要每日 |
| 空值處理 | 三態（有價／200 無資料／失敗）分開存；**絕不把「無資料」寫成 0 或 null 價格**，否則下降偵測會誤判 |
| 429/403 | 當作終止條件：停止、記錄、不重試、不換 IP／UA（本次腳本即此行為） |
| 401 | 重取首頁一次再重試（48h 效期）；仍失敗則放棄該輪 |
| key 管理 | 每次執行從首頁現取，**不硬編碼**；日誌只印遮罩值 |
| 監控 | 記錄每輪 `priced_ratio`；若連續兩週 < 50%，視為資料源不可用並告警 |
| 驗證 | 週期性用官網／促銷卡對照（本次已證明促銷卡不可信，只能當「不一致訊號」） |

### 8.3 尚未釐清（建議下一輪）

- 覆蓋率是否隨**觀測時間**變化（同一組日期連續數週觀測，看 11/07 是否某週突然出現票價）→ 這是區分「資料集缺漏」與「開賣時間」的唯一方法。
- 其他航線（KIX/FUK/CTS…）覆蓋率是否同樣 38%，或與航線熱門度相關。
- `travelClasses` / `priceBuckets.field` 的組合對覆蓋率的影響（本次固定 `ECONOMY` + `TOTAL_PRICE`）。
