## 2. 候選方案

### 🟢 方案 A：資料可信度守門員（reliability）
> 核心精神：**「壞資料永遠不進 repo，壞了立刻知道」**

| # | 項目 | 內容 |
|---|------|------|
| A1 | 驗證層 | schema 驗證（必填欄位/型別）、價格 sanity range（2,000–200,000 TWD）、異常偵測（同航線同週新價 vs 歷史中位數 >2.5x / <0.4x）、缺週檢查；輸出驗證報告 `api/status.json` |
| A2 | 驗證 gate | workflow 驗證失敗 → 不 commit（不污染歷史）+ 告警 |
| A3 | 主動告警 | Telegram bot（失敗 / 異常 / 跳過 commit / 成功摘要可選） |
| A4 | CI | push/PR 自動跑 Python 驗證測試 + `node --test` + Playwright E2E |

### 🔵 方案 B：前端產品化（frontend）
> 核心精神：**「讓訪客更快看到圖、更容易分享、更願意回來」**

| # | 項目 | 內容 |
|---|------|------|
| B1 | Route 合併檔 | `api/routes/{route}.json` → 首次載入 40 請求 → 2 請求 |
| B2 | 上週變動 badge | 每週 ↑↓ 差幅（今天買 vs 下週買）；hover 顯示與平均差幅 |
| B3 | URL 深連結 | `?route=TPE-KIX&range=6m&flight=JX 800` 可分享、可收藏 |
| B4 | CSV 匯出 | 一鍵匯出目前視圖 |
| B5 | 表格視圖 | 圖表/表格 toggle（a11y 加分＋快速掃描） |

### 🟡 方案 C：合併兩期（最終採用）
- 一期（地基）：A1 + A2 + A3 + B1
- 二期（加分）：A4 + B2 + B3 + B4 + B5

**關鍵取捨**：
- 🔍 **取捨 #1：可信度是「地基」，體驗是「裝潢」**。價格資料一旦被污染（現在零防護），前端再漂亮使用者也不會信 → A 為必須，B 為加分。
- 🔍 **取捨 #2：分期 vs 一次做完**。投入規模不確定 → 分期風險最低，一期完成隨時可停。
- 🔍 **取捨 #3：Telegram 引入**。約束已允許放寬；Telegram 完全 $0、GitHub Actions 內發送、不需伺服器，不破壞「純靜態」原則。

## 4. 決策理由

### 為什麼選擇此方案（完整兩期）
1. 使用者直接指定「全部」——reliability 與 frontend 並重，符合「好產品」目標
2. A 系列保護資料可信度（產品的地基），B 系列提升使用者體驗（產品的門面），兩者互補不衝突
3. 分期設計：一期（守門員 + 合併檔）是性價比最高的地基組合，做完隨時可停、可交付

### 為什麼放棄其他方案
- **只做 A（守門員）**：忽略了使用者體驗，與「做出好產品」目標不符
- **只做 B（前端）**：資料無防護下前端再好也難建立信任
- **只做部分**（如不要 CI / 不要表格）：使用者已明確要全部；分期已提供彈性

### 共識程度
✅ 團隊一致（使用者於收斂階段直接指定「全部」）

### 環境建置步驟（Telegram 告警）
1. Telegram 建立 bot：`@BotFather` → `/newbot` → 取得 `TELEGRAM_BOT_TOKEN`
2. 取得個人 chat id：對 bot 發一則訊息 → `https://api.telegram.org/bot<TOKEN>/getUpdates` → `chat.id`
3. repo Settings → Secrets and variables → Actions 新增：
   - `TELEGRAM_BOT_TOKEN`（bot token）
   - `TELEGRAM_CHAT_ID`（個人 chat id）
4. workflow 於 failure 步驟用 `curl` 呼叫 sendMessage（不需要第三方 action）

### 第三方服務與設定方向
| 服務 | 用途 | 成本 | 設定 |
|------|------|------|------|
| Telegram Bot | 主動告警 | $0 | 上述 secrets 兩枚 |
| GitHub Actions | 爬蟲 + 驗證 + CI | $0（public repo 免費額度） | `ci.yml` + `weekly-crawl.yml` |
| GitHub Pages | 靜態託管 | $0 | 既有（Deploy from main / root） |

### 有待驗證的項目（Spike）
- **異常偵測門檻**：2.5x / 0.4x 是否會誤報？以既有 120 筆 TPE-NRT 資料回測；若誤報多改為動態 IQR
- **route 合併檔大小**：minify（去掉縮排）後預估 <40KB/航線，確認行動網路載入體驗
- **CI 中 Playwright**：`e2e_smoke.py` 使用 `/usr/bin/chromium`；ubuntu-latest 需 `apt install chromium-browser` 或 `playwright install chromium`，Spike 確認最簡方式
- **Telegram rate limit**：每週一次爬蟲 + 告警，遠低於限額，無虞

### 後續（本輪不做，資料累積後再評估）
- 跨航空比較（長榮/華航/日航）— 需個別 API 研究，最大工作量
- 每日抓取 ＋ 多出發日組合 — 提升決策價值
- 年度對比（去年此時價格）— 需 ≥1 年資料
- 季節性分析 / 「比歷史平均便宜 X%」標籤 — 需更多歷史

## 6. 風險登錄

| 風險 | 可能性 | 影響 | 緩解措施 |
|------|--------|------|---------|
| Telegram token 外洩 | 低 | 中 | Secrets 管理；bot 僅授權 sendMessage；token 可隨時撤銷重建 |
| 異常偵測誤報（首次抓取無歷史基準） | 中 | 低 | 無歷史時跳過異常偵測，只做 sanity range；Spike 回測門檻 |
| 前端改版破壞既有功能 | 中 | 中 | 依賴既有 unit + e2e 測試網；分期合併小步提交 |
| route 合併檔與 trips 檔雙軌不一致 | 中 | 低 | 兩者由同一 build_api.py 產生；過渡期後移除 trips 檔並更新 index |
| 價格長期漲跌使固定門檻失真 | 低 | 中 | 定期檢視；必要時改動態 IQR（Spike 已列） |
| GitHub Actions 額度（CI 增加用量） | 低 | 低 | public repo 免費額度充足（2000 分/月，每週僅數分） |
