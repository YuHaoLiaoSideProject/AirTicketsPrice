## 1. 需求回顧（共識摘要）

| 項目 | 共識 |
|------|------|
| 核心價值 | 再次開啟頁面「快取優先 + 增量更新」：有網路時只補載新增/變更，沒網路時直接看上次快取，保留手動更新 |
| 使用者 | 公開訪客（免登入）；再次開啟 / 書籤 / 分享連結進入 |
| 5 情境 | A 首次訪問（需連網全量載入 + 寫快取）；B 連網無新版（秒開 + 「已是最新」，零 trip 請求）；C 連網有新版（只補載變更）；D 離線（快取 + 離線橫幅，圖表全功能可用）；E 手動更新（強制重新驗證） |
| 異常 | E1 首次即離線錯誤卡＋重試；E2 離線切未載入航線提示；E3 背景比對失敗不中斷瀏覽＋稍後自動重試；E4 部分更新失敗保留舊版；E5 空間不足降級；E6 伺服器 404 移除本地快取；E7 離線手動更新停用；E8 無痕/另一瀏覽器＝首次訪問 |
| 邊界 | 離線可看範圍僅限「上次成功載入過」的航線；快取以瀏覽器為單位、不跨裝置；比對基準 `generated_at`；首次訪問仍需連網 |
| 資料容量 | index ~9KB + 159 檔 × ~1-2KB ≈ **250KB**，正常瀏覽器配額內；仍需 E5 降級設計 |
| 驗收 | 情境 B 秒開且**未重新抓取任何 trip 檔**；情境 C 只補載變更；情境 D 離線全功能可用；既有功能無回歸 |

**現況事實（本次審計確認）**：
- 前端快取僅 `routeCache` 記憶體 Map（`web/app.js`），**無任何持久化**（無 localStorage / IndexedDB / Service Worker）→ 每次開啟都全量重抓
- `index.json` 目前以 `cache:'no-cache'` 抓取（每次重新驗證）；trip 檔以 concurrency 8 並行載入
- 159 個 trip 檔路徑依航線目錄分段（`api/trips/{ROUTE}/{dep}_{ret}.json`），可從 `index.trips` 依路徑段篩出各航線清單
- B1（`api/routes/{route}.json` 合併檔）**尚未實作**；本決策以現行結構為準，但 schema 設計預留相容
- 單元測試 `node:test`（Node v22.23.1）可 `require` UMD 模組；E2E Python Playwright（67 checks）可 `context.setOffline()` 模擬離線
- 部署 GitHub Pages（root 靜態託管）→ HTTPS 環境，Service Worker 可正常註冊（`file://` 下無 SW，降級為純記憶體快取）

## 2. 候選方案

### 🟢 方案 A：Service Worker（Cache Storage）為核心的完整離線
SW 攔截**所有**請求（app shell + `api/`），以 Cache Storage 為主儲存；資料層邏輯（比對、增量）也放進 SW 或在 SW 內做 cache-first / network-first 策略。

| 內容 | 說明 |
|------|------|
| 技術 | `web/sw.js` 攔 `api/*` + Cache Storage 版本管理 |
| 優點 | 離線能力最完整（含 API 回應層快取）；瀏覽器層級兜底 |
| 缺點 | **雙層快取**（SW Cache + 資料層）除錯複雜；增量「只補載變更」仍需 JS 決定 URL，SW 只是第二個會失效的層；SW 更新生命週期（activate/clients/skipWaiting）對單人維護是淨負擔；E2E 模擬離線＋SW 互動最難測 |

### 🟡 方案 B：純 JS 持久化快取（IndexedDB/localStorage）+ 增量同步，無 Service Worker
所有資料（index + trips）存 IndexedDB，JS 層做比對與增量；頁面殼依賴瀏覽器 HTTP 快取離線開啟。

| 內容 | 說明 |
|------|------|
| 技術 | `web/cache.js`（IDB 封裝）+ 現有 `app.js` 改 cache-first |
| 優點 | 無 SW 概念，邏輯全部純函式可測；與現有架構差異最小 |
| 缺點 | **情境 D「離線開啟頁面」無法保證**：GitHub Pages HTML 的 `Cache-Control: max-age=600` 僅 10 分鐘，冷啟動（重開瀏覽器/飛航模式）離線開頁**賭 HTTP 快取運氣**，不達驗收；「秒開」也少了 SW 的殼快取 |

### 🔵 方案 C：混合（輕量 SW 只快取靜態資源 + JS 層資料增量同步）（**當選**）
SW 極簡：只 precache app shell 5 檔（index.html / styles.css / aggregate.js / app.js），SWR 策略，**不攔 `api/`**；資料層完全在 JS（IndexedDB + 比對 + 條件式增量），與 interaction flow 的資料語意一一對應。

| 內容 | 說明 |
|------|------|
| 技術 | `web/sw.js`（~40 行）+ `web/cache.js`（IDB + 純函式）+ `app.js` 改 cache-first |
| 優點 | 情境 D 離線開頁 100% 達標（殼在 Cache Storage）；資料邏輯留在 JS 純函式可測；SW 只有 5 個靜態檔無失效難題；B1 相容天然 |
| 缺點 | 比 B 多一個 SW 檔與註冊邏輯；比 A 少一層（API 不進 SW） |

| 維度 | 🟢 A 全 SW | 🟡 B 純 JS | 🔵 C 混合（採用） |
|------|:---:|:---:|:---:|
| 🎯 需求符合度（5 情境全覆蓋） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐（情境 D 開頁不保證） | ⭐⭐⭐⭐⭐ |
| ⚡ 開發速度 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 🔧 維護成本（單人） | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 📈 擴充性（B1 / 多頁未來） | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 👥 團隊熟悉度 | ⭐⭐⭐（SW 生命週期） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 💰 基礎設施成本 | $0 | $0 | $0 |
| 🔒 穩定性與可測性 | ⭐⭐⭐（雙層快取難測） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 🧪 測試覆蓋難度（離線 E2E） | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |

**關鍵取捨**：
- 🔍 **取捨 #1：情境 D 的「離線開頁」是硬需求**。沒有 SW，頁面殼離線開啟只能靠瀏覽器 HTTP 快取（GitHub Pages HTML 僅 max-age=600）——冷啟動即失敗，驗收清單「離線・有快取：顯示快取趨勢圖」無法穩定達標 → 排除方案 B。
- 🔍 **取捨 #2：增量邏輯該住哪一層**。interaction flow 的核心（比對 `generated_at`、只補載變更、部分失敗、404 移除）是**資料層語意**，不是網路層語意。放在 SW（方案 A）等於把可純函式測試的邏輯丟進難測的 SW 環境，還多一個會失效的快取層 → 資料邏輯一律留 JS，SW 只當「殼的保命符」。
- 🔍 **取捨 #3：SW 的攔截範圍**。SW 只攔 app shell、不攔 `api/`：API 請求行為維持 `app.js` 可預測（離線時資料層主動不發請求，不會被 SW 半路接走造成「看似連線」的假象）。

**最終選擇**：方案 C。A 的完整離線收益在資料規模（~250KB）下不抵其雙層快取維運成本；B 無法保證情境 D；C 以最小 SW（5 檔）補齊離線開頁，資料層維持「純 JS + 純函式測試」的既有路線。

## 4. 決策理由

### 為什麼選擇方案 C
1. **情境 D 是驗收硬需求，只有 SW 能保證**：GitHub Pages HTML 快取僅 10 分鐘，冷啟動離線開頁唯有 SW 的 Cache Storage 可靠；而 C 只用 SW 兜 app shell 5 檔，生命週期問題最小化。
2. **資料層邏輯全部留在 JS 純函式**：比對 / 增量 / 降級決策做成 `web/cache.js` 純函式，沿用 `aggregate.js` 的 UMD + `node --test` 路線，零新測試工具；E2E 用 Playwright `setOffline()` 即可測，不必與 SW 生命週期搏鬥。
3. **與 B1（route 合併檔）天然相容**：快取 schema 抽象為「route → unit 清單」，B1 後 unit 從 159 個 trip 檔變 4 個 route 檔，比對 / 增量 / ETag 機制完全不變——本決策不鎖死現行 API 結構。

### 為什麼放棄其他方案
- **方案 A（全 SW）**：API 進 SW 造成雙層快取（SW Cache + IndexedDB），失效與除錯成本對單人專案不成比例；增量「只補載變更」本質是資料語意，放 SW 反而難測；SW 更新生命週期（新 SW 接管、clients）在此規模是純負擔。
- **方案 B（純 JS 無 SW）**：情境 D「離線開啟頁面 → 顯示快取趨勢圖」無法穩定達標——頁面殼只能靠瀏覽器 HTTP 快取（max-age=600）離線開啟，重開瀏覽器即失效；也不享受 SW 的殼秒開（情境 B/C 的「快取秒開」）。
- **localStorage（D2 的次選）**：同步 API 在寫入 ~250KB 時阻塞主執行緒；私有模式（E8）例外最多；無法與 SW 共用。IndexedDB 在同等 $0 成本下全勝。

### 與既有決策的一致性
- 不破壞純靜態原則：SW 是瀏覽器原生能力、IndexedDB 是瀏覽器原生能力，皆**無伺服器、無建置、零第三方依賴**（不用 workbox / idb npm 套件）。
- 沿用「零依賴純函式 + 腳本化驗證」的 D5/D6 決策：新模組 `cache.js` 比照 `aggregate.js` UMD 模式，`node --test` 直接覆蓋。

### 快取 Schema（`web/cache.js` 的 IndexedDB 結構）

```
db: airtickets-cache (version 1)
  store "meta":  { version: 1, generatedAt: ISO, syncedAt: ISO,
                   routeLoadedAt: { routeId: ISO }, lastError: null|'partial'|'compare_failed' }
  store "units": { [routeId]: { [unitUrl]: { etag: string|null, json: object } } }
                  ↑ unitUrl 今天 = api/trips/{route}/{dep}_{ret}.json；B1 後 = api/routes/{route}.json
```

- **B1 相容（D7）**：`routeUnitsFromIndex(index)` 是唯一的「index → unit 清單」映射點。今天：`index.trips` 依路徑段 `/{route}/` 篩出各航線 trip URL；B1 後：`index.routes` → `api/routes/{route}.json`。比對 / 增量 / ETag / 降級機制全部不動；僅 bump `version` 觸發一次全量重同步。
- **ETag 來源**：首次成功抓取時讀 `res.headers.get('etag')` 存入；同步時回送 `If-None-Match`。GitHub Pages 若不回 ETag 或無視條件式請求（回 200）→ 直接覆寫快取，功能正確、僅少掉增量節省（見 Spike S1）。

### 同步決策純函式（全部 `node --test` 覆蓋）

| 函式 | 輸入 → 輸出 | 對應情境 |
|------|-------------|---------|
| `decideSync(cachedGeneratedAt, serverGeneratedAt)` | `'fresh' \| 'update' \| 'stale'`（`Date.parse` 比較；解析失敗視為 update） | B / C / 過舊警示 |
| `diffUnits(cachedUnits, serverUnitList)` | `{ added: [], kept: [], removed: [] }`（URL 集合差） | C（新增/滑出 40 週視窗） |
| `applyUnitResult(units, url, status, json, etag)` | 依 status 更新：200 覆寫、304 保留、404 刪除（E6）、錯誤保留＋標記 | C / E4 / E6 |
| `routeUnitsFromIndex(index)` | `{ [routeId]: [unitUrl...] }` | 現行結構 + B1 變體 |
| `quotaDegrade(units, keepRoute)` | 只保留 keepRoute 的 units（E5） | E5 |

### 初始流程（`app.js` 改寫後）

```
init():
  1. 註冊 SW（僅 http(s) 且 'serviceWorker' in navigator；失敗靜默降級）
  2. 讀 IndexedDB meta/units
     ├ 無 meta（首次 / E8 無痕）→ 情境 A：全量載入（維持 concurrency 8）→ 寫快取
     └ 有 meta → 立即以快取繪圖（秒開）+ 「上次更新 HH:MM」
  3. navigator.onLine === false → 離線橫幅 + 不發請求 + E2 降級
  4. 連網 → 背景比對（E3 失敗 → 「更新失敗，稍後自動重試」+ online 事件重試）
     → decideSync：
       fresh → 「已是最新」
       update → 目前航線先同步 → 其餘航線低優先背景同步（全部航線離線可用）
       stale → 「資料可能過時」警示（沿用 staleBar）
  5. 同步期間互動不阻塞；完成後若目前航線資料變更 → 重繪 + 更新時間更新
  6. E5：IDB 寫入 QuotaExceededError → quotaDegrade(目前航線) + 「空間不足，已保留最新資料」
  7. E8：IDB 開啟失敗（無痕）→ 降級為現有記憶體 routeCache 行為（頁面仍可用）
```

### 有待驗證的項目（Spike）

| # | 項目 | 驗證方式 | 若失敗的備援 |
|---|------|---------|-------------|
| S1 | **GitHub Pages ETag / If-None-Match 支援** | `curl -I` 看 ETag header；帶 `If-None-Match` 發條件式請求看是否回 304 | 回 200 全量覆寫（功能正確）；B1 後僅 4 檔/航線，增量價值反而上升 |
| S2 | **Playwright `setOffline(true)` + SW reload** | 先正常載入等 `navigator.serviceWorker.ready` → `setOffline(true)` → `page.reload()` → 驗證殼與資料都來自快取 | 改用「route 攔截全部失敗」模擬離線（不碰真網路） |
| S3 | **IndexedDB 私有模式 / 儲存配額行為** | Safari 無痕與 Chrome incognito 實測 open 是否拋錯 | E8 降級記憶體快取（現有行為），頁面仍可用 |
| S4 | **304 空 body 的 fetch 處理** | `res.status === 304` 分支在 Chromium/Firefox/WebKit 一致 | 統一以 status 判斷，不讀 body |

### 本輪不做（明確排除）
- **PWA 安裝性**（manifest + icons / installable）：interaction flow 未要求，避免擴大 scope
- **背景週期同步**（Background Sync / Periodic Sync）：以「開啟頁面時比對」滿足情境，不需要
- **跨裝置 / 登入同步**：interaction flow 邊界明列「不跨裝置」，維持瀏覽器為單位
- **B1 route 合併檔實作**：屬優化方向一期，另行排程；本決策僅保證 schema 相容

## 6. 風險登錄

| 風險 | 可能性 | 影響 | 緩解措施 |
|------|--------|------|---------|
| GitHub Pages 不支援條件式請求（S1） | 中 | 低 | 回 200 即覆寫，功能正確僅少增量節省；B1 後增量顆粒度變大（4 檔）更無感 |
| SW 雙層互動除錯（殼快取 vs 資料層） | 低 | 中 | SW 只攔 5 檔、不攔 `api/`；cache name 版本化；E2E 覆蓋離線 reload |
| `generated_at` 相同但內容已變（伺服器未更新時間戳） | 低 | 低 | 無法由比對偵測；A1 驗證層（缺週/異常檢查）降低發生率；手動更新為使用者自救 |
| 40 週滑窗：檔案離開列表但伺服器未刪（仍在線） | 低 | 低 | `diffUnits.removed`（不在新清單）→ 一律移除本地快取（E6 語意） |
| IndexedDB 無痕/配額失敗（E5/E8） | 中 | 低 | try/catch 降級：E5 只保留目前航線、E8 降級記憶體快取；Spike S3 實測 |
| 既有 67 個 E2E check 回歸 | 中 | 中 | 新功能獨立 `e2e_offline.py`，先跑 `e2e_smoke.py` 全綠再合併；cache-first 改寫不更動聚合純函式 |
| SW 更新後舊 cache 殘留 | 低 | 低 | `activate` 刪除非目前 cache name；版本號隨部署 bump |
| 離線誤判（`navigator.onLine` 不準） | 低 | 中 | 以實際請求失敗為準（interaction flow 明列）；offline/online 事件即時修正橫幅與按鈕 |
