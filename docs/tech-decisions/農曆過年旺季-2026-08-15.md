## 3. 決策理由

### 為什麼選擇此方案
1. **農曆過年是「計算問題」不是「資料問題」**：正月初一由天文朔日決定，`lunardate` 實測 2026~2029 全部正確，0 外部依賴、`$0`、可單元測試 — 完全符合專案「零維運」精神。
2. **管道零成本**：`api/index.json` 已是前端唯一入口且有 ETag 驗證，加一個 `peaks` 欄位即完成，不動 trips 語意、不加請求數。
3. **向後相容**：前端保留硬編碼 fallback，舊資料與離線快取不受影響，測試不需破壞性修改。

### 為什麼放棄其他方案
- **香港天文台文字檔**：每年要改檔名、解析固定寬度文字、引入網路依賴 — 維運成本比手動改日期還高；僅作為 holidays.py 的獨立對照（測試用）。
- **行政院行事曆**：無 API 且發布時間晚於爬蟲視窗頭段，無法滿足「自動帶出」。
- **免費假日 API（timor.tech 等）**：實測被 Cloudflare 擋（403），不可靠。
- **櫻花季自動化**：無免費 API、季節性預報（每年 1 月中才發布）、四航線花期差一個月（札幌 5 月初）— 自動化收益低於成本，維持手動並分航線設定是更務實的下一步。
