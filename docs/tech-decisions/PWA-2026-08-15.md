## 2. 候選方案

### 🟣 方案 A：全託管簡化 — OneSignal 免費版
manifest/icons/iOS/audit 與其他方案共用；推播部分交給 OneSignal Web Push SDK 免費 tier（10k 訂閱者）。

| 內容 | 說明 |
|------|------|
| 技術 | OneSignal SDK + 其免費 tier；後台管理訂閱者 |
| 優點 | 最快落地（半天）；SDK 成熟；後台可看訂閱者／發送紀錄 |
| 缺點 | 第三方依賴（外站 JS、資料經 OneSignal、免費 tier 政策風險）；學習價值最低；品牌與資料控制權外流 |

### 🟢 方案 B：自建輕量 — Cloudflare Workers + VAPID Web Push（**Phase 2 採用**）
一個 ~150 行 Cloudflare Worker（Web Push endpoint + Workers KV 存訂閱名單）+ 前端訂閱 UI + GitHub Actions 爬蟲後呼叫 Worker 發通知。

| 內容 | 說明 |
|------|------|
| 技術 | CF Workers free tier（100k req/day）＋ Workers KV（1GB）＋ VAPID（Web Crypto 簽章）＋ `web-push` 協定 |
| 優點 | **完全免費且自主**（無第三方品牌、資料自己掌握）；學習價值最高（符合 learning 價值）；免費配額對 <50 人綽綽有餘 |
| 缺點 | 需實作 VAPID/Web Push（含 Spike：Web Crypto on Workers）；GitHub 需引入 1 個 repo secret；維護一個 Worker |
| 適用 | 長期自主、技術學習、親友規模 |

### 🟡 方案 C：混合兩階段（**當選**）
- **Phase 1（先做，所有方案共用）**：manifest + 圖示 + iOS + Lighthouse 達標 → 可安裝 App（~1–2 天）
- **Phase 2（後做）**：推播通知 → 採用**方案 B**（自建 Cloudflare Worker）

| 內容 | 說明 |
|------|------|
| 技術 | Phase 1 純前端增量；Phase 2 CF Worker + VAPID |
| 優點 | 先拿到可安裝價值、風險隔離；每階段可交付、可回歸；時程無壓力所以兩階段都完整做 |
| 缺點 | 比 A 慢；比「直接做 B」多一次部署週期（但單人專案無感） |

## 4. 決策理由

### 為什麼選擇方案 C（兩階段 + 自建推播）
1. **維持 $0 與自主**：Cloudflare Workers 免費 tier 完全滿足 <50 人親友團需求；不引入 OneSignal 等第三方品牌與資料外流。VAPID 私鑰與訂閱名單全部自己持有。
2. **符合技術學習價值**：VAPID 簽章（Web Crypto）、Web Push 協定、KV 儲存、安裝體驗——正是 side project 練功的完整技術棧；OneSignal 只是「貼 SDK」。
3. **兩階段風險隔離**：可安裝 PWA 是純前端增量（~1–2 天、低風險、立刻可回歸）；推播是唯一需要外部端點的複雜功能，獨立成 Phase 2 並先做 Spike，避免一次大改動造成既有離線功能回歸。

### 為什麼放棄其他方案
- **方案 A（OneSignal）**：最快但不是「學習」；免費 tier 政策非自控；外站 SDK 與資料外流與本專案「純靜態、零第三方」的一貫原則衝突；後台管理面在 <50 人規模下價值極低。
- **直上方案 B（一次到位）**：技術上可行，但把可安裝（低風險）與推播（含 Spike 的高風險）綁在一次改動，回歸面大；兩階段對單人無額外成本，沒有理由不分。
- **「先做 Phase 1、推播之後再評估」**：使用者已確認兩階段都做（時程無壓力），此選項等同本決策的執行順序，僅保留「Phase 2 開工前再確認一次」的檢查點。

### 有待驗證的項目（Spike）

| # | 項目 | 驗證方式 | 若失敗的備援 |
|---|------|---------|-------------|
| S1 | **CF Workers 上 Web Push（VAPID 用 Web Crypto）** | 小型 spike：在 Worker 以 Web Crypto 產生 VAPID JWT 簽章（ES256）並呼叫 push service endpoint；或評估 `@block65/webcrypto-web-push` 等無 Node crypto 依賴的實作 | 改用 Vercel/Netlify 免費 function（Node 環境可用 `web-push` npm 套件）；再不行退回 OneSignal（決策復議） |
| S2 | **GitHub Pages 子路徑下 SW scope 與 manifest start_url** | 實測 `https://…/AirTicketsPrice/web/` 安裝後的 start_url / scope / notification click 開啟路徑 | 統一用相對路徑 `./`，通知 deep-link 以 `registration.scope` 為基準拼接 |
| S3 | **iOS 16.4+ 推播實際行為** | 親友實機（iOS Safari → 加到主畫面 → 訂閱）驗證；無 iPhone 則以文件註記為 MAN-XX 手動驗證項目 | 保守提示「iOS 需加到主畫面」；通知失敗不影響頁面功能 |
| S4 | **Lighthouse installable 通過條件** | 跑 Lighthouse 確認 maskable icon / SW 控制 / manifest 完整度都 pass | 依稽核錯誤逐一補齊（多為 manifest 欄位或 icon purpose） |


### 本輪不做（明確排除）
- **below_avg / new_low / 週摘要觸發**：使用者只選了 drop_last；架構（Worker + notify payload）已預留擴充，未來加條件只需改爬蟲端偵測與 payload
- **每日爬蟲**：維持每週；通知頻率與爬蟲同頻
- **訂閱者管理後台 / 退訂清單介面**：親友規模，subscribe/unsubscribe 由前端按鈕處理即可；KV 直接管理
- **多帳號 / 登入**：維持公開免登入
- **iOS push 的「未安裝」fallback（如 email）**：超出範圍，維持「僅安裝後可收」的誠實提示

## 6. 風險登錄

| 風險 | 可能性 | 影響 | 緩解措施 |
|------|--------|------|---------|
| CF Workers 上 VAPID 簽章實作複雜（S1） | 中 | 高 | Phase 2 第一件事就是 Spike；失敗備援 Vercel/Netlify function（用 `web-push` 套件），最後才是 OneSignal 復議 |
| iOS 推播限制（僅 installed PWA、16.4+） | 高 | 低 | D5/D7 明列並誠實提示；S3 實機驗證；影響面僅 iOS 用戶 |
| GitHub repo secret 引入（打破「零 Secrets」） | 中 | 低 | 僅 1 個 secret（`PUSH_API_TOKEN`）；README 明示；若外洩可輪換 token |
| 每週一次頻率下「上次比較基準」 | 低 | 低 | 以「上一週 `data/*.json` 原始檔」為基準（`scraped_at` 小於本次的最大者；**不可用 `api/latest.json`**——notify 前已被本次 build_api.py 覆寫，見開發規格 §1.3 陷阱）；首次無基準時跳過通知（只建立基準） |
| 通知轟炸 / 親友退訂 | 低 | 低 | 合併單則摘要（最多 3 條）；前端一鍵退訂；SW `notificationclose` 處理 |
| 既有離線功能回歸 | 中 | 高 | Phase 1 純前端增量、`e2e_smoke`/`e2e_offline` 為回歸門檻；SW 改動（push handler）不更動既有 shell precache 邏輯，僅 bump cache version |
| 安裝按鈕出現時機（beforeinstallprompt 行為差異） | 中 | 低 | 標準 deferred prompt 流程；iOS 以 UA hint 顯示「加到主畫面」步驟（S3 實測） |
| Lighthouse 稽核條件變動 | 低 | 低 | 以「可安裝（Installable）+ 離線 + best practices 無 regression」為驗收，不追求特定工具版本分數 |
